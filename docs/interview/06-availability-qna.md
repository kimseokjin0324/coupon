## Q1. 대기열을 왜 Redis Sorted Set(ZSET)으로 만들었나?

**배경**: 대기실이 하는 일은 세 가지다.
1. 진입: `ZADD NX score=진입시각 userId`
2. 상태 조회 "나는 몇 번째?": `ZRANK userId`
3. 드레인: 매초 `ZRANGE 0 99` 후 `ZREM`

**내 답변**
> ZSet이 순서대로 FIFO를 할 수 있는 걸로 알고 있다. 순위가 있는 Set이라서 그런 것 같다.

**정리**
- 절반은 맞다. 그런데 **FIFO는 Redis List(`RPUSH`/`LPOP`)로도 된다.** 그래서 "FIFO라서"만으로는 이유가 되지 않는다.
- 진짜 이유는 "순위가 있는 **Set**"의 두 단어에 있다.

| 이유 | List | ZSET |
|---|---|---|
| **순위**: 내 순번 조회 | `LPOS`로 앞에서부터 비교, O(N) | `ZRANK`, O(log N) (skip list) |
| **Set**: 새로고침 중복 진입 | `RPUSH` 두 번 → 줄에 두 번 섬 | member가 유일 + `ZADD NX`로 **최초 진입 시각 유지** → 순번이 밀리지 않음 |

- Redis는 싱글 스레드라, 폴링마다 O(N) 명령이 몰리면 다른 모든 요청이 그 뒤에서 기다린다.

| 대안 | 선택하지 않은 이유 |
|---|---|
| Redis List | 순번 조회 O(N), 중복 진입을 막지 못함 |
| Kafka | 순서대로 꺼내기는 되지만 "이 사람이 몇 번째인지"는 조회 불가 |
| MySQL 테이블 | 순번 조회마다 `COUNT(*)`, 폴링 부하가 DB로 가서 DB 보호라는 목적과 반대 |
| 서버 메모리 큐 | 서버마다 줄이 따로 생겨 전역 FIFO와 전역 통과 속도가 깨짐 |

**면접용 한 문장**
> "FIFO만 필요하면 List로 충분하지만, 대기실은 폴링마다 내 순번을 조회해야 해서 O(log N)인 `ZRANK`가 필요했고, 새로고침 중복 진입을 막으면서 최초 순번을 유지하려고 member 유일성과 `ZADD NX`를 썼습니다."

## Q2. 드레인을 왜 ShedLock으로 한 서버에서만 돌렸나?

**배경**: `RedisWaitingRoom.drain()`은 `@Scheduled(fixedRate = 1000)`이라 **서버마다** 실행된다. `@SchedulerLock`으로 락을 잡은 1대만 실제로 드레인한다.

**질문 1.** ShedLock을 빼면 서버 2대에서 초당 몇 명이 통과하나?

**내 답변**
> 초당 200명이 통과할 것이다. 각 서버가 둘 다 드레인하니까.

**정리**: 정답이다. 덧붙이면 **같은 사람이 두 번 통과하지는 않는다.** 꺼내기(`ZRANGE`)와 지우기(`ZREM`)가 Lua 안에서 원자적으로 처리돼서 두 서버가 서로 다른 100명씩을 가져간다. 정합성 문제가 아니라 **통과 속도가 서버 수에 비례해 늘어나는 것**이 문제다.

**질문 2.** ShedLock 없이 고치는 다른 방법은?

**내 답변**
> Kafka를 쓰면 되지 않을까. 그런데 리소스를 너무 많이 쓸 것 같다.

**정리**: "한 곳에서 처리하게 하자"는 방향은 맞다. 그런데 Kafka로 바꿔도 "누가 1초에 한 번 100명을 꺼낼 것인가"는 그대로 남는다(컨슈머도 결국 서버 안에서 돈다). Q1처럼 순번 조회도 못 한다.

| 대안 | 방식 | 약점 |
|---|---|---|
| **ShedLock** (선택) | 락을 잡은 1대만 드레인 | 락을 잡은 서버가 죽으면 `lockAtMostFor`(10s)까지 드레인이 멈춤 → Q7 |
| 서버별로 나눠 꺼내기 | 각자 `100 / N`명씩 | N을 정확히 알아야 함. 오토스케일링 순간 속도가 틀어짐 |
| 초 단위 슬롯 키 | `SET drain:{쿠폰}:{현재초} NX`에 성공한 서버만 드레인 | 사실상 직접 만든 락, 검증된 라이브러리 대신 직접 구현 |
| 드레인 전용 워커 | 별도 프로세스 1개만 드레인 | 배포 단위가 늘고, 그 워커가 단일 장애점 |
| Kafka | 큐를 Kafka로 | 드레인 주체 문제가 그대로 남고, 순번 조회 불가, 리소스 부담 |

**근거 (직접 측정)**: 5-1 scale 테스트에서 서버 2대에서도 입장권 2,000건 / 20초 = **약 100건/s**

**면접용 한 문장**
> "`@Scheduled`는 서버마다 실행되기 때문에 2대면 통과 속도가 2배가 됩니다. 서버 수로 나누는 방식은 오토스케일링 때 N이 바뀌면 틀어지므로, 서버 수와 상관없이 1대만 실행되도록 ShedLock 분산 락을 썼고, scale 테스트에서 2대에서도 100건/s가 유지되는 것을 확인했습니다."

## Q3. 통과를 왜 별도 입장권 키로 표시했나? TTL은 왜 30초인가?

**배경**: 드레인은 사용자를 ZSET에서 `ZREM`으로 지우고, 같은 Lua에서 `SET waiting:{쿠폰}:pass:<userId> 1 PX 30000`을 만든다. 발급 API는 이 키의 존재만 확인한다.

### Q3-1. 입장권 없이 "ZSET 순번 100 이하면 통과"로 판단하면?

**내 답변**
> 모르겠다.

→ 힌트: 철수는 150번째. 1초 드레인 후 50번째가 돼서 통과. 클릭 직전 2초 드레인이 또 돈다. 철수는 ZSET에서 (a) 50번째 (b) 1번째 (c) 지워짐?

**내 답변**
> c

**정리**
- 정답. 드레인이 지운 순간 ZSET만으로는 두 경우를 구분할 수 없다.

| 실제 상황 | ZSET에서 보이는 모습 |
|---|---|
| 정상적으로 통과함 | 없음 |
| 대기실에 들어온 적이 없음 (발급 API 직접 호출) | 없음 |

- 그래서 지우는 순간 **같은 Lua 안에서** 통과 기록(입장권)을 남긴다. 발급 API는 키가 있으면 통과, 없으면 `403 NO_WAITING_ROOM_PASS`.
- "지우지 말고 남겨 두면?" 앞사람이 그대로라 다음 100명을 꺼낼 수 없다. 몇 번째까지 통과시켰는지를 따로 관리해야 한다. **줄과 통과 명단은 하는 일이 다르니 자료구조도 나눈다.**

**면접용 한 문장**
> "드레인이 대기열에서 사용자를 꺼내 지우면 '통과한 사람'과 '진입한 적 없는 사람'을 구분할 수 없어서, 꺼내는 Lua 안에서 원자적으로 입장권 키를 발급하고 발급 API는 그 키 존재만 검사하도록 대기열과 통과 명단을 분리했습니다."

### Q3-2. TTL이 없으면 생기는 문제는? (a) 메모리 누적 (b) 나중에 줄 안 서고 발급 (c) 드레인 정지 (d) userId 공유로 언제든 진입

**내 답변**
> a, b, d

**정리**: 정답. (c)는 관련 없다(드레인은 ZSET만 보고, 입장권은 쓰기만 한다).

| | TTL 없음 | TTL 30초 |
|---|---|---|
| (a) 메모리 | 발급을 안 한 통과자의 키가 계속 쌓임 | 30초 뒤 자동 정리 |
| (b) 재사용 | 몇 시간 뒤에도 줄을 서지 않고 발급 | 지금 차례가 온 사람만 |
| (d) 공유 | 언제든 진입 가능 | 30초 안으로 **범위가 줄어듦** (해결은 아님) |

- **트레이드오프**: 너무 짧으면 정상 사용자가 클릭하기 전에 만료된다. 너무 길면 (b)와 (d)가 가능한 시간이 길어진다. 30초는 측정으로 정한 값이 아니라 **정책값**이다.
- (d)의 근본 원인은 서버가 `X-User-Id` 헤더를 그대로 믿는다는 점이다. → Q7

**면접용 한 문장**
> "입장권에 30초 TTL을 둬서 미사용 키가 자동 정리되고, 한 번 통과한 사람이 나중에 줄을 건너뛰지 못하게 했습니다. 너무 짧으면 정상 사용자가 클릭 전에 만료되는 트레이드오프가 있어서, 사람이 반응하기에 충분한 정책값으로 잡았습니다."

## Q4. 대기 상태를 왜 폴링으로 알려 주나?

**배경**: 클라이언트가 1초(+ 지터 0~0.25초)마다 `GET /api/waiting-room/{id}`로 통과 여부를 묻는다. 대안은 서버가 먼저 알려 주는 SSE / WebSocket.

**질문.** 폴링을 택한 이유로 맞는 것은? (a) 연결 10만 개 유지 부담 (b) 서버 여러 대일 때 알림 주체 문제 (c) 폴링이 가볍고 측정상 부담이 작음 (d) 폴링이 항상 더 빠름

**내 답변**
> c, b, a

**정리**: 정답. (d)는 틀렸다. 폴링은 최대 폴링 간격(약 1초)만큼 늦게 알 수 있고, 푸시가 더 빠르다.

| 이유 | 설명 |
|---|---|
| (a) 연결 유지 비용 | 대기자 10만 명이면 WebSocket/SSE 연결 10만 개를 계속 붙잡아야 한다. 대기실은 트래픽이 몰릴 때 서버를 보호하려고 만든 것인데, 연결 유지 자체가 부하가 된다 |
| (b) 다중 서버 알림 | 사용자가 연결된 서버 ≠ 드레인을 실행한 서버일 수 있다. 통과 사실을 해당 서버로 전달하려면 Redis Pub/Sub 같은 브로드캐스트 계층이 하나 더 필요하다 |
| (c) 측정상 부담이 작음 | 폴링 1회 = Redis Lua 1회. 사용자당 평균 **1.375회**, 폴링 P95 **11.25ms** (5-2 journey) |

- **트레이드오프**: 통과 알림이 최대 약 1초 늦다. 지터(0~0.25초)는 모든 클라이언트가 같은 순간에 몰려서 폴링하는 것을 막으려고 넣었다.
- 대기자 수가 아주 많으면 폴링 간격을 순번에 비례해 늘리는 방법도 있다. (예: 1만 번째면 10초 간격. 미구현)

| 대안 | 장점 | 선택하지 않은 이유 |
|---|---|---|
| **폴링** (선택) | Stateless, 서버 수와 무관, 구현 단순 | 알림이 최대 1초 늦고 대기 중 요청이 계속 발생 |
| SSE | 단방향 푸시, HTTP 기반 | 연결 유지 비용, 다중 서버 알림 전달 계층 필요 |
| WebSocket | 양방향, 실시간 | SSE의 단점 + 프록시/게이트웨이 설정 복잡 |

**면접용 한 문장**
> "대기실은 트래픽이 몰릴 때 서버를 보호하려는 장치라, 대기자마다 연결을 붙잡는 푸시 방식은 그 자체가 부하가 되고 서버가 여러 대면 알림 전달 계층도 따로 필요합니다. 폴링은 Redis 조회 한 번이라 가볍고, 측정해 보니 사용자당 평균 1.4회, P95 11ms여서 폴링을 택했습니다. 대신 통과 알림이 최대 1초 늦는 건 감수했습니다."
