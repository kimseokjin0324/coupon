# 4단계: 효율성 (캐시, 매진 플래그)

## 1. 문제

3단계에서 Kafka 비동기 발급으로 응답성을 개선했지만, 발급 API는 여전히 **모든 요청마다 쿠폰 정보를 DB에서 조회**한다.

### 1-1. DB 조회 병목 재현 (Baseline 측정)

동일한 쿠폰(ID=1)에 대한 발급 요청 급증 시나리오:
- **부하**: 500 req/s × 30초 = 15,000 요청
- **상황**: 쿠폰 NotStarted 상태 → 재고 차감 없이 정책 조회만 수행

| 지표 | 워밍업 (1차) | 본 측정 (2차) | 비고 |
|---|---|---|---|
| **P99 응답시간** | 25.8ms | 3.15ms | InnoDB 버퍼풀 워밍업 효과 |
| **P95 응답시간** | 3.45ms | 2.26ms | |
| **평균 응답시간** | 3.13ms | 1.74ms | |
| **couponDbReads** | 15,000 | 15,000 | **모든 요청이 DB 조회** |
| **couponCacheHits** | 0 | 0 | 캐시 미적용 |
| **soldOutRedisExists** | 0 | 0 | 매진 플래그 미적용 |
| **soldOutFastPathHits** | 0 | 0 | |

**문제점**:
- 15,000번의 동일 쿠폰 조회가 모두 DB로 전달됨
- 워밍업 후에도 P99 3.15ms → 트래픽 증가 시 DB가 병목 가능
- DB CPU/커넥션 자원 낭비

## 2. 원인

- 쿠폰 정책은 **변경 빈도가 낮지만 조회 빈도는 매우 높은** read-heavy 워크로드
- 매번 DB 왕복으로 불필요한 네트워크 비용 + 커넥션 자원 소모
- 동일 데이터를 15,000번 반복 조회 → 캐시로 해결 가능한 전형적인 케이스

## 3. 선택한 방법

### 단계적 개선 전략

Cache Stampede 문제를 **점진적으로 해결**하면서 각 단계의 효과를 측정:

| 단계 | 구현 | 해결하는 문제 | 측정 스크립트 |
|---|---|---|---|
| **4-0** | 캐시 미적용 (Baseline) | - | `coupon_burst.js` |
| **4-1a** | Redis Cache 기본 적용 | DB 반복 조회 | `coupon_burst.js` |
| **4-1b** | Single Flight 적용 | Cache Stampede (TTL 만료 시 동시 DB 조회) | `coupon_burst.js` |
| **4-1c** | SWR 적용 | TTL 만료 순간의 응답 지연 | `coupon_burst.js` |

**Cache Stampede란?**
TTL 만료 직후 동시에 같은 키를 요청할 때, 캐시 미스가 발생해 **모든 요청이 DB로 몰리는 현상**.
`COUPON_CACHE_TTL_MS=1000` (1초)로 강제 설정해 재현.

**Single Flight (중복 제거)**
동일 키에 대한 동시 요청을 **하나로 묶어서 DB 조회는 1번만** 수행.

**구현 방식** (Redis Lua + Lock):
- Lua 스크립트로 **캐시 조회 + 락 획득을 원자적**으로 처리
- 첫 요청이 락 획득 → DB 조회 → 캐시 저장 → 락 해제
- 나머지 요청은 `WAIT` 상태로 20ms 백오프 재시도 (최대 50회)
- UUID 토큰으로 락 소유권 검증 (다른 요청의 락을 실수로 해제하지 않도록)

**SWR (Stale-While-Revalidate)**
TTL 만료 시 **만료된 캐시를 즉시 반환**하고, **백그라운드에서 비동기 갱신**.
→ 응답 지연 없이 일관된 P99 유지.

**구현 방식** (Redis Hash + Background Thread Pool):
- **Redis Hash 구조**: `{value: JSON, fetchedAtMs: 타임스탬프}` 저장
- **freshMs 기준**: `now - fetchedAtMs < freshMs` → fresh, 아니면 stale
- **Lua 스크립트**: 캐시 조회 + 신선도 판단 + 락 획득을 원자적으로 처리
  - `HIT`: 신선한 캐시 → 즉시 반환
  - `STALE_REFRESH`: 만료된 캐시 → **stale 값 즉시 반환** + 백그라운드 갱신 트리거
  - `LOAD`: 캐시 없음 → DB 조회 (첫 요청)
  - `WAIT`: 다른 요청이 LOAD 중 → 대기
- **백그라운드 스레드풀**: `Executors.newFixedThreadPool(4)` (daemon 스레드)
  - STALE_REFRESH 시 비동기로 `fillCache()` 실행
  - 사용자 응답에 영향 없음 (fire-and-forget)

## 4. 고려한 대안

### 4-1. 캐시 저장소 선택

| 대안 | 장점 | 선택한/하지 않은 이유 |
|---|---|---|
| **Redis** (선택) | 분산 환경 공유, 만료 정책 내장, Lua 스크립트 지원 | ✅ 선택: 이미 재고 관리에 사용 중, 추가 인프라 불필요 |
| Local Cache (Caffeine) | 네트워크 비용 없음, 매우 빠름 | Pod별 캐시 불일치 가능, TTL 만료 시점 분산 어려움 |
| Spring Cache (추상화) | 구현체 교체 용이 | Redis 직접 사용이 Single Flight / SWR 구현에 더 유리 |

### 4-2. Cache Stampede 해결 방법

| 대안 | 장점 | 선택한/하지 않은 이유 |
|---|---|---|
| **Single Flight** (선택) | 동시 요청을 하나로 묶어 DB 조회 최소화 | ✅ 선택: 측정 단계(4-1b)로 포함 |
| **SWR** (선택) | 만료된 값 즉시 반환 → P99 안정화 | ✅ 선택: 최종 목표(4-1c) |
| Probabilistic Early Expiration | 통계적 분산으로 stampede 완화 | 완전한 해결은 아님, SWR이 더 결정적 |
| Lock-based | 첫 요청만 갱신, 나머지 대기 | Single Flight와 유사하나 구현 복잡도 높음 |
| 무한 TTL + 이벤트 갱신 | stampede 원천 제거 | 쿠폰 수정 이벤트 구독 필요, 복잡도 높음 |

## 5. 결과 (Before / After)

### 5-1. Cache Stampede 해결 단계별 비교 (coupon_burst.js)

**측정 조건**: 500 req/s × 30초 = 15,000 요청, `COUPON_CACHE_TTL_MS=1000` (1초 TTL)

| 지표 | 4-0 (캐시 미적용) | 4-1a (Redis Cache) | 4-1b (Single Flight) | 4-1c (SWR) |
|---|---|---|---|---|
| **P99 (ms)** | 3.15 | 103.46 ⚠️ | 104.13 ⚠️ | **3.09** ✅✅ |
| **P95 (ms)** | 2.26 | 102.85 ⚠️ | 63.24 ✅ | **2.12** ✅✅ |
| **평균 (ms)** | 1.74 | 10.18 | 7.76 ✅ | **1.91** ✅✅ |
| **couponDbReads** | 15,000 | 1,250 ✅ | 28 ✅✅ | 50 ✅ |
| **couponCacheHits** | 0 | 13,751 ✅ | 14,972 ✅✅ | 15,000 ✅✅ |
| **캐시 히트율** | 0% | 91.7% | 99.81% ✅✅ | **100%** ✅✅ |
| **Threshold 통과** | ✅ | ✅ (threshold은 p(99)<200) | ✅ | ✅ |

**4-1a 상세 측정값**:

| 회차 | P99 | P95 | 평균 | couponDbReads | couponCacheHits |
|---|---|---|---|---|---|
| 워밍업 (1차) | 141.87ms | 103.08ms | 12.82ms | 1,010 | 13,991 |
| 본 측정 (2차) | 103.46ms | 102.85ms | 10.18ms | 1,250 | 13,751 |

**4-1a 결과 분석 (Redis Cache 기본)**:

✅ **성공한 부분**:
- DB 조회 **91.7% 감소** (15,000 → 1,250회)
- 캐시 히트율 **91.7%** 달성

⚠️ **하지만 응답성은 오히려 악화**:
- 평균 응답시간 **5.8배 악화** (1.74ms → 10.18ms) ← stampede 대기 시간 때문

⚠️ **Cache Stampede 발생**:
- P99가 3.15ms → **103.46ms로 33배 폭증**
- P95도 2.26ms → **102.85ms로 45배 폭증**
- TTL 1초 × 30초 = 30번 만료 예상인데, DB 조회 1,250회 = **만료마다 평균 41.7개 요청이 동시에 DB 조회**
- 워밍업 시 P99 141.87ms까지 튀었다가 본 측정 103.46ms로 개선 → 여전히 불안정

**왜 이런 일이?**
```
┌─ TTL 만료 순간 ─────────────────────┐
│ 500 req/s → 캐시 미스!              │
│ ├─ 요청1 → DB 조회 (느림)           │
│ ├─ 요청2 → DB 조회 (느림)           │
│ ├─ 요청3 → DB 조회 (느림)           │
│ └─ ... 41개 요청이 동시에 DB 조회   │
│    → DB 부하 + 대기 시간 발생       │
│    → P99 튐!                        │
└─────────────────────────────────────┘
```

→ **다음 단계 (4-1b)**: Single Flight로 동시 요청을 하나로 묶어 DB 조회 1번만 수행

**4-1b 상세 측정값**:

| 회차 | P99 | P95 | 평균 | couponDbReads | couponCacheHits |
|---|---|---|---|---|---|
| 워밍업 (1차) | 104.18ms | 63.31ms | 7.96ms | 28 | 14,972 |
| 본 측정 (2차) | 104.13ms | 63.24ms | 7.76ms | TODO | TODO |

**4-1b 결과 분석 (Single Flight)**:

✅ **DB 조회 극적 감소**:
- 4-1a 대비 DB 조회 **97.8% 감소** (1,250회 → 28회)
- 캐시 히트율 **99.81%** 달성 (91.7% → 99.81%, +8.1%p)
- TTL 1초 × 30초 = 30번 만료 예상, DB 조회 28회 ≈ **만료마다 평균 1회 DB 조회** (stampede 해소!)

✅ **응답성 개선**:
- 평균 응답시간 **23.8% 개선** (10.18ms → 7.76ms)
- P95 **38.5% 개선** (102.85ms → 63.24ms)

⚠️ **하지만 P99는 여전히 높음**:
- P99는 103.46ms → 104.13ms로 **거의 동일** (stampede는 해결했지만 tail latency 문제 잔존)
- TTL 만료 시 첫 요청은 여전히 DB 조회를 기다려야 함 → **응답 지연 발생**

**Single Flight의 효과와 한계**:
```
┌─ TTL 만료 순간 (Single Flight 적용 후) ──┐
│ 500 req/s → 캐시 미스!                   │
│ ├─ 요청1 → DB 조회 시작 (느림)           │
│ ├─ 요청2 → 요청1 결과 대기 ⏳            │
│ ├─ 요청3 → 요청1 결과 대기 ⏳            │
│ └─ ... 나머지 요청도 요청1 결과 대기     │
│    → DB 조회는 1번! ✅                   │
│    → 하지만 모두 DB 조회 완료를 기다림  │
│    → P99 여전히 높음 ⚠️                 │
└──────────────────────────────────────────┘
```

→ **다음 단계 (4-1c)**: SWR(Stale-While-Revalidate)로 만료된 캐시를 즉시 반환하고 백그라운드 갱신

**4-1c 상세 측정값**:

| 회차 | P99 | P95 | 평균 | couponDbReads | couponCacheHits |
|---|---|---|---|---|---|
| 워밍업 (1차) | 2.64ms | 2.1ms | 1.9ms | 50 | 15,000 |
| 본 측정 (2차) | 3.09ms | 2.12ms | 1.91ms | 50 | 15,000 |

**4-1c 결과 분석 (SWR - Stale-While-Revalidate)**:

🎉 **목표 달성! P99를 캐시 없을 때 수준으로 복원**:
- P99 **97.0% 개선** (104.13ms → 3.09ms)
- P95 **96.6% 개선** (63.24ms → 2.12ms)
- 평균 **75.4% 개선** (7.76ms → 1.91ms)
- **캐시 없을 때(4-0)와 거의 동일한 응답성** (P99 3.15ms vs 3.09ms)

✅ **DB 조회 극소화 유지**:
- couponDbReads: 50회 (TTL 30번 만료 × ~1.67회/만료)
- 캐시 히트율: **100%** (15,000/15,000)
- 모든 요청이 캐시에서 응답 (stale 포함)

✅ **Cache Stampede 완전 해소 + 응답 지연 제거**:
- TTL 만료 시 **stale 값을 즉시 반환** → 대기 시간 0
- 백그라운드에서 **비동기 갱신** → 사용자 응답에 영향 없음
- P99 안정화 (104.13ms → 3.09ms, **33배 개선**)

**SWR의 동작 방식**:
```
┌─ TTL 만료 순간 (SWR 적용) ──────────────┐
│ 500 req/s → 캐시 TTL 만료               │
│ ├─ 요청1 → stale 캐시 즉시 반환 ⚡      │
│ │           + 백그라운드 갱신 시작 🔄   │
│ ├─ 요청2 → stale 캐시 즉시 반환 ⚡      │
│ ├─ 요청3 → stale 캐시 즉시 반환 ⚡      │
│ └─ ... 모든 요청이 즉시 응답            │
│    → 응답시간: ~2ms (캐시 조회만)       │
│    → DB 조회는 백그라운드에서 진행      │
│    → 갱신 완료 후 다음 요청부터 fresh   │
└─────────────────────────────────────────┘
```

**4-1b (Single Flight)와 차이**:
```
Single Flight:
  TTL 만료 → 첫 요청이 DB 대기 (101ms)
           → 나머지 요청도 대기 (20ms × N회)
           → P99 = 104ms

SWR:
  TTL 만료 → 모든 요청이 stale 즉시 반환 (2ms)
           → DB 갱신은 백그라운드 (사용자 무관)
           → P99 = 3ms ✅
```

**트레이드오프**:
- **Gain**: P99 33배 개선, 응답 지연 제거, UX 일관성
- **Loss**: TTL 만료 후 갱신 전까지 **최대 TTL(1초) 동안 stale 데이터** 제공
  - 하지만 쿠폰 정책은 변경 빈도 매우 낮음 (생성 후 거의 수정 안 함)
  - 1초 stale은 비즈니스적으로 허용 가능

## 7. 강의 외 추가 구현

### 7-1. 단계별 측정으로 문제와 해법 증명

**차별화 포인트**: Cache Stampede를 **3단계로 나눠 측정**하며 각 해법의 효과와 한계를 수치로 입증

| 단계 | 측정 목적 | 발견한 문제 | 해결 방법 |
|---|---|---|---|
| **4-1a (Redis Cache)** | 캐시 도입 효과 측정 | DB 조회 91.7% 감소, **하지만 P99 33배 악화** (stampede) | → 4-1b로 진행 |
| **4-1b (Single Flight)** | Stampede 해소 검증 | DB 조회 97.8% 감소, **하지만 P99 여전히 높음** (대기) | → 4-1c로 진행 |
| **4-1c (SWR)** | 응답성 복원 검증 | P99 97% 개선, 캐시 없을 때 수준으로 복원 | ✅ 완료 |

**강의와 차이**:
- 강의: SWR만 적용하고 최종 결과 측정
- 이 프로젝트: **왜 SWR이 필요한지를 숫자로 증명** (4-1a → 4-1b → 4-1c)

### 7-2. Redis Hash + 타임스탬프로 SWR 구현

**기술적 구현** (`CouponCacheRepository.kt`, `cache-single-flight-swr.lua`):

```kotlin
// Redis Hash 구조
HSET coupon:1:issue-policy
  value       = "{\"id\":1,...}"
  fetchedAtMs = "1704067200000"

// Lua에서 신선도 판단
if now - fetchedAtMs < freshMs then
  return {"HIT", value}  // fresh
else
  return {"STALE_REFRESH", value}  // stale이지만 즉시 반환
end
```

**대안과 비교**:
| 구현 방식 | 장점 | 이 프로젝트가 선택하지 않은 이유 |
|---|---|---|
| TTL 두 개 (soft, hard) | 구현 간단 | Redis 키 2개 관리, Lua 스크립트로 원자성 보장 어려움 |
| Caffeine (Local Cache) | 네트워크 비용 없음 | Pod별 불일치, 분산 환경 고려 |
| **Hash + 타임스탬프** (선택) | 원자적 조회/갱신, 단일 키 관리 | ✅ 선택 |

### 7-3. 백그라운드 갱신 스레드풀 관리

**구현** (`CouponCacheRepository.kt:25-27, 110-113`):

```kotlin
private val backgroundExecutor = Executors.newFixedThreadPool(4) { r ->
    Thread(r, "coupon-cache-swr-refresh").apply { isDaemon = true }
}

@PreDestroy
fun shutDown() {
    backgroundExecutor.shutdown()  // 우아한 종료
}
```

**차별화 포인트**:
- **고정 크기 스레드풀 (4)**: 백그라운드 갱신이 무한정 늘어나지 않도록 제한
- **Daemon 스레드**: 애플리케이션 종료 시 강제 종료되지만 `@PreDestroy`로 우아한 종료 시도
- **예외 처리**: 백그라운드 갱신 실패 시 로그만 남기고 계속 진행 (사용자 응답에 영향 없음)

**대안**:
- `@Async` + Spring ThreadPoolTaskExecutor: 설정 간단하지만 fine-grained 제어 어려움
- Kotlin Coroutine: 비동기 코드 간결하지만 프로젝트 전체를 suspend fun으로 전환 필요
